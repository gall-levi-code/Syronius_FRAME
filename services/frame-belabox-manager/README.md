# FRAME Belabox Manager

Belabox integration scaffold for FRAME.

The operator page stays at `/belabox` behind FRAME login and is not exposed through the Hybrid public gateway. Runtime device traffic uses authenticated MQTT over WebSockets at `/mqtt`, so roaming Belabox devices only need outbound HTTPS/WSS access back to FRAME.

Normal setup is Pair / Repair: enter the Belabox SSH host, username, and either a password or private key. FRAME validates SSH, provisions device credentials internally, writes the agent config, installs/repairs the boot service, and waits for the MQTT heartbeat with live UI progress. MQTT credentials and signing keys are not shown in the UI. Uninstall Agent removes FRAME-owned services and archives the Belabox-local `~/.frame-belabox-agent` folder. Remove Device From FRAME deletes FRAME-side credentials, ACLs, retained broker status, and cached dashboard state.

The FRAME-owned remote belaUI surface is `/belabox/remote?key=<device_id>`. In Hybrid mode this route is allowed through the public gateway, then protected by the same FRAME login middleware as the local Belabox manager. The public shell polls `/belabox/remote/status?key=<device_id>` and shows an immediate offline page until the encoder control surface is reachable. Once online, the shell loads the per-device proxy route through the agent's outbound WSS session; it does not require FRAME to know or reach the Belabox LAN address. The proxy rewrites stock belaUI asset paths and WebSocket scheme/path handling without patching stock belaUI files.

Internally, provisioning generates a unique MQTT username/password per device and writes Mosquitto ACLs so each device can only use `frame/belabox/{device_id}/...`. FRAME signs command requests with Ed25519; the agent verifies signatures, expiry, nonce, device ID, and the allowlist before running any action.

Allowed commands include agent status/restart/update stubs, telemetry refresh, photo transport controls, processing controls, and upload diagnostics. SSH checks only run when both `BELABOX_SSH_ENABLED=true` and `BELABOX_AGENT_COMMANDS_ENABLED=true`; Pair / Repair and Uninstall Agent use explicit SSH maintenance credentials. The sample agent lives in `agent/belabox-agent.mjs` and reads `BELABOX_MQTT_URL`, `BELABOX_MQTT_USERNAME`, `BELABOX_MQTT_PASSWORD`, `BELABOX_DEVICE_ID`, `BELABOX_COMMAND_SIGNING_PUBLIC_KEY_B64`, and the `BELABOX_REMOTE_BELAUI_*` settings for the FRAME-owned remote belaUI target.

Network diagnostics run latency, download, and upload measurements sequentially on route-checked IPv4 interfaces. Requests bind to the interface source address and can target either Cloudflare's external speed service or FRAME's authenticated `/belabox-chunks/api/diagnostics/speed-test` endpoint. Tests are intentionally uncapped and can compete with an active stream.

The managed photo workflow is deployed as `frame-belabox-photo-agent.service` under `~/.frame-belabox-agent/photo-agent`. The photo agent stages stable camera files, keeps a small upload-ready processed spool, and streams chunk bytes from the processed JPEG without writing chunk files to disk. Pillow is the preferred single-decode JPEG processor and preserves EXIF/ICC metadata; ImageMagick remains a fallback. The main Belabox agent continuously writes `egress.json` with route-checked source-IP lanes; `photo-agent.py` consumes that snapshot during `chunked_https` uploads, forces IPv4 for FRAME requests, and binds both control requests and chunk workers to healthy source addresses before falling back to the default route.

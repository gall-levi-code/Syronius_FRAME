# FRAME Launcher release acceptance

Installer CI produces **release candidates**, not evidence that a download is ready for public
distribution. Signing setup remains deferred until explicitly authorized; this checklist does not
require credentials to be added to source or shared in a chat. Record the exact commit, version,
artifact SHA-256, OS version, architecture, tester, date, and result for each acceptance run.

## Automated candidate checks

`.github/workflows/build-installer.yml` builds on Windows Server 2022, Ubuntu 22.04, macOS 15 Intel,
and macOS 15 ARM64 runners. Its existing behavior tests run before packaging. Each native runner
then uses development Electron with the built renderer and real preload/shell, a temporary profile,
and a simulated backend. The smoke checks:

- Window creation and reopening; native Mac menu/Dock activation on macOS.
- Renderer sandboxing, context isolation, and absence of renderer Node access.
- Native Tab focus on Home and no horizontal overflow at 900×640 with 200% Chromium zoom.
- The window fallback when tray creation is deliberately made unavailable.
- No Docker commands, login-item registration, or notification delivery.

`npm run smoke:native` runs the same isolated smoke locally after `npm run build`. It briefly opens
a test window; on Linux it needs a graphical session (CI uses Xvfb). The parent process removes the
temporary profile after Electron exits, including on Windows where Chromium holds profile locks.
Do not add sandbox-disabling flags to make this check pass.

`scripts/check-artifacts.mjs <win|linux|mac> <x64|arm64>` verifies the exact expected download names,
rejects missing/stale/wrong-architecture or empty outputs, and streams each package through SHA-256.
ARM64 packages are currently produced only for macOS. AppImage x64 filenames use **x86_64**, as
generated by the pinned electron-builder version. Each candidate artifact includes:

- The NSIS EXE, AppImage, or both Mac DMG and ZIP.
- `SHA256SUMS-<platform>-<arch>.txt` and `artifact-check-<platform>-<arch>.json`.
- `native-smoke-<platform>-<arch>.json`, including what the smoke did and did not verify.

Checksums identify the bytes tested; they do not prove the publisher's identity. This smoke does not
launch the packaged application, install/uninstall it, exercise FUSE or Gatekeeper, deliver a real
notification, or test native OS display scaling. A successful CI run cannot substitute for the
downloaded-package checks below. No native macOS/Linux smoke result or signed release acceptance
is claimed by merely adding these gates.

## Downloaded-package gates

Use the exact candidate downloaded from the intended release channel in a normal user account,
including its ordinary download/quarantine marking. Use a disposable test deployment and media.
Do not mark a row passed from a source-tree Electron run.

| Platform / package | Required native acceptance | Evidence still required |
| --- | --- | --- |
| Windows 11 x64 / NSIS EXE | Verify Authenticode signatures on the installer and installed executable, including the expected publisher and timestamp. Install without administrator privileges where supported; launch from the Start Menu; upgrade an existing launcher; uninstall the launcher and confirm FRAME configuration/data remain. Record SmartScreen behavior rather than assuming signing removes every prompt. | Signed downloaded installer, clean install/upgrade/uninstall, shortcut identity, notification click, sign-in preference. |
| Intel Mac / x64 DMG and ZIP | Verify Developer ID signing, hardened runtime and notarization; validate the stapled ticket where applicable. Open the downloaded DMG and ZIP normally, copy the app to Applications, and launch under Gatekeeper. Test replacement of an older launcher, Dock/menu-bar reopening and the login-item approval flow. | Real Intel Mac, downloaded signed/notarized artifacts, first launch, upgrade, notification and login-item behavior. |
| Apple silicon Mac / ARM64 DMG and ZIP | Repeat Mac acceptance with the native ARM64 package and confirm no Rosetta dependency. | Real Apple silicon Mac and native artifacts; the Intel result does not cover ARM64. |
| Ubuntu 22.04 LTS x64 / AppImage | Execute the downloaded file as a normal user with its expected FUSE runtime, and confirm Chromium sandbox startup. Test GNOME with and without a reachable tray. | Actual AppImage first launch; development Electron under Xvfb does not cover it. |
| Ubuntu 24.04 LTS x64 / AppImage | Repeat on the default GNOME session, recording X11/Wayland and AppArmor behavior. | Actual AppImage, FUSE dependency and sandbox compatibility with the host's default security policy. |
| Debian 12 x64 / AppImage | Repeat on a named desktop/session and record available tray/notification services. | Native Debian acceptance; an Ubuntu CI build does not establish Debian compatibility. |

The Linux rows are named acceptance targets, not a claim that every distribution or session is
supported. The AppImage needs executable permission. The currently pinned builder uses the FUSE 2
runtime: Ubuntu 22.04/Debian use `libfuse2`; Ubuntu 24.04 names that library `libfuse2t64`.
Install only the needed compatibility library according to the distribution's documentation; do
not replace its FUSE 3 installation. See the [AppImage FUSE guide](https://docs.appimage.org/user-guide/troubleshooting/fuse.html).

Ubuntu can restrict unprivileged user namespaces through AppArmor. If the AppImage cannot start
with its sandbox enabled, record a failed gate and investigate a narrowly scoped packaging/policy
solution before claiming support. Do not ship `--no-sandbox`, disable the host's AppArmor policy, or
run the launcher as root as the default workaround. See [Ubuntu's AppArmor documentation](https://documentation.ubuntu.com/security/security-features/privilege-restriction/apparmor/)
and [Electron process sandboxing](https://www.electronjs.org/docs/latest/tutorial/sandbox/).

## Interaction and host integration

For each accepted downloaded package, record these results separately from container health:

1. Use Tab/Shift+Tab, Enter/Space and Escape through Home, My Setup, setup, Updates & repair, and
   Preferences. Confirm visible focus, labels, confirmation/cancellation, error announcements, and
   access to the footer. Include the platform's screen reader where available.
2. Test native display scaling at 100%, 150% and 200%, a 900×640 window, and a larger display.
   Include a move between displays with different scaling. Verify text, buttons, paths and logs remain
   readable and reachable; Chromium zoom alone does not prove this.
3. Enable notifications and exercise a real service-state change and available-update notification.
   Verify its app identity and click-to-reopen behavior. Disable notifications and verify silence.
   Test the OS-denied/Do Not Disturb case without treating missing delivery as successful delivery.
4. Test tray/menu-bar availability and a session without a tray. Closing must never hide the only
   usable launcher window. Reopen when a tray is reachable; Quit must end monitoring without stopping
   FRAME. Test the Mac Dock separately.
5. Test the packaged Windows/macOS sign-in preference, including OS approval where required. It must
   launch only the launcher and must not override deliberately stopped FRAME services. Linux must
   continue to show this preference as unsupported.
6. Complete first setup and exercise actual Docker/media workflows on the intended architecture.
   Check Portal, photo upload/gallery/stage and the configured audio/video tools. Accept health checks
   as service readiness evidence, not proof of working cameras, encoders, audio feeds or OBS output.

Windows notifications depend on installed application identity and shortcuts; see
[Electron's notification requirements](https://www.electronjs.org/docs/latest/tutorial/notifications).
Use the signing guidance for the pinned builder version,
[electron-builder v26 Windows signing](https://www.electron.build/v26/docs/features/code-signing/code-signing-win/), and
[Apple's notarization documentation](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).
Keep release credentials in the authorized signing environment. Record signature verification and
native first-launch evidence before treating a candidate as accepted.

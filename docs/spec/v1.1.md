## 0.0 - What This Stack Is (For New IRL Streamers)

**Syronius’ Frame (F.R.A.M.E.)** stands for:

> **F**ederated **R**elay & **A**utomation for **M**edia & **E**xperiences

It is a **self-hosted control center for IRL streaming and live photography**, designed to orchestrate everything *around* your stream — not just the video feed.

If you are:

- transitioning from studio streaming to IRL,
- a photographer who wants tighter control over how images appear on stream,
- or someone who wants to reduce manual glue between OBS, StreamerBot, cameras, and overlays,

F.R.A.M.E. exists to make live production **predictable, observable, and intentional**.

At a high level, the stack helps you:

- **Relay live media reliably** (video, audio, photos)
- **Automate decisions and timing** instead of reacting live
- **Federate tools** like OBS, StreamerBot, cameras, and browsers into one system
- **Present media intentionally** on stream and remotely

All of this is done **locally and under your control**, with optional remote access for web pages only.

---

### A) Why These Problems Matter in IRL Streaming

IRL streaming is uniquely difficult because:

- your network conditions change constantly
- you are often multitasking (walking, shooting, talking, navigating)
- you cannot afford fragile or manual workflows
- small failures compound quickly on stream

This stack exists to **reduce cognitive load while live** by making:

- ingest reliable
- automation predictable
- visual presentation intentional

Instead of fighting tools mid‑stream, you configure behavior *before* you go live.

---

### B) Goals

#### Primary Goals

- Self‑hosted **SRTLA ingest** with management UI
- Robust **photo ingest pipeline** with JPG‑only normalization
- Deterministic **StreamerBot handoff** using `.ready` manifests
- **OBS overlays** with a wizard and live preview
- **Hybrid mode** (Cloudflare Tunnel for HTTP only)
- **Remote Audio Monitor** (Windows source, AAC, always‑on)

## 1.0 - High‑Level UX

### A) Installation & Reconfiguration UX

The stack ships with a single installer entrypoint (`stack.sh` for Linux/macOS and `stack.cmd` for Windows) that supports subcommands. 

Supported commands (V1):

- **install**

  - Installs or reconfigures the environment.
  - Prompts the user to build/update `.env` and `/data` structures.
  - Generates/updates `docker-compose.yml` and `stack-config.json`.
  - Validates prerequisites (Docker + Compose).
  - Validates **port conflicts** and halts on conflicts.
  - Deploys the stack (`docker compose up -d`) with selected profiles.
  - Re-running `install` allows enabling/disabling features and switching **LAN vs Hybrid**.
  - Shows a full breakdown of previous setup (or fresh install details).
  - Option: set services to be **always-on** (container restart policy `restart: always`).

- **start**

  - Brings up the container stack (`docker compose up -d`).
  - If config is missing, prompts the user to run `install`.

- **stop**

  - Stops the container stack (`docker compose down`).
  - If config is missing, prompts the user to run `install`.

- **status**

  - Prints installation status and service/container state.
  - Reports container uptime when available.
  - Lists enabled capabilities from `stack-config.json`.
  - Prints current `.env` values with sensitive fields **redacted**.

- **reset**

  - Destructive reinstall.
  - Stops and removes containers (and associated volumes where applicable).
  - Deletes the repository-local data directory, when `FRAME_DATA_ROOT` is repository-local.
  - Leaves absolute external data roots intact.
  - Re-runs the interactive `install` flow to recreate `.env` and generated data scaffolding.
  - Requires explicit confirmation.

*Updates are out of scope for V1.*

### B) Configuration Persistence

- Feature choices persist across runs
- Data is never deleted when disabling features
- Only the `reset` path removes data

### C) Modes

- **LAN-Only** – everything local
- **Hybrid** – HTTP via Cloudflare Tunnel, ingest + FTP stay LAN (requires cloudflared token)

### D) Portal (Unified Navigation Shell)

A dedicated **Portal service** provides a shared navigation and landing experience.

- Nav is **not hardcoded**
- Nav is generated dynamically from `stack-config.json`
- Each item reflects:
  - Enabled / Disabled
  - Ready / Needs setup / Offline

The portal links to (never iframes) other UIs.

The implemented `frame-portal` service lives in `services/frame-portal/`. It provides `/dashboard`,
`/status`, `/status/api`, and SSE container logs. Portal navigation uses the same generated
`stack-config.json` that drives installer capability and route decisions.

Protected FRAME Edge routes use the shared `/auth/login` form. A successful Portal login returns
the browser to its original route and creates one signed session shared across the FRAME hostname
for seven days by default. The Portal must display when fallback configuration is active and
distinguish Ready, Needs setup, Offline, and Disabled tools.

Authentication credentials and session cookies must only be transported publicly over HTTPS.
Direct service ports retain their service-level authentication behavior as a development and
recovery fallback.

### E) Dashboard

Single landing page linking to:

- Stream Management (SLS UI)
- Overlay Wizard + generated OBS URLs
- Today Gallery / Viewer / Remote Controller
- Manual Upload
- Audio Monitor Admin + Listen links
- Discord Audio Bridge status; private operator links remain bot-provided
- System Status

### B) Reverse Proxy

- Traefik (internal routing)
- Optional Cloudflared (Hybrid mode)

### C) SRTLA + SLS

- OpenIRL `srtla-receiver`
- FRAME-owned `frame-streams` management UI against the receiver API
- **Dependency:** SLS UI requires SRTLA receiver
- SLS Stream IDs become **Stream Profiles** usable by overlays

### D) Overlay Server

- FRAME-owned Express renderer, V2 source/preset store, and shared telemetry hub in one container
- Connectivity telemetry plus web-upload, FTP ingest, and Belabox upload-progress adapters are
  implemented; photo-pipeline lifecycle correlation remains a follow-up
- Includes:
  - Source / Preset / Template studio and 1:1 live preview
  - Immutable built-in templates and reusable user presets
  - Keyed, permanent OBS sources with placement controls (`dock`, `pad`, `scale`)
  - SSE telemetry/config revisions with a source-scoped REST fallback

#### Telemetry Stats Source

Default stats URL pattern (from `frame-ingest-video`):

- `http://<host-ip>:8080/stats/<play-id>`

Notes:

- `<play-id>` is derived from the SLS Stream Profile.
- The overlay server treats stats as best-effort, polls each stream profile once regardless of OBS
  client count, and caches normalized samples with sequence, timestamp, and stale state.
- Renderers keep the last healthy sample through brief failures and show a clear "NO SIGNAL" only
  after the sample becomes stale or the publisher is confirmed disconnected.

#### Stream Profile Sync (V1)

The Overlay Wizard populates its stream profile selector by polling the `frame-ingest-video` stream-ID API through the FRAME overlay service. No shared file or cross-container DB read is required.

- The wizard polls on **page load** and on an explicit **"Refresh" button** action.
- No continuous background polling.
- If the stats endpoint is unreachable, the wizard shows an empty selector with a "No streams available — check SRTLA receiver" message.

#### Overlay Ownership and Persistence (V2)

- `default-connectivity` is an immutable built-in template and the `default_template_id`; stock
  templates cannot be edited or deleted.
- User presets contain reusable design, layout, theme, and widget configuration only. They do not
  contain stream bindings, source keys, slugs, or public URL identity.
- Sources bind one preset to one data source and own `/overlays/view/<slug>/<source-key>`, where the
  key is randomly generated and unguessable.
- V1 `/overlays/view/<preset-id>` URLs remain valid through deterministic legacy aliases created
  when `/data/state/overlay-presets.json` migrates to schema `2.0`.
- Migrations back up the V1 state. Every mutation is schema validated, serialized, revisioned,
  backed up, and atomically renamed from a unique temporary file. Stale management revisions
  receive `409 Conflict`.

**Dependencies (V1 default UX):**

- Bitrate overlay requires **SRTLA receiver** (stats source)
- Overlay Wizard requires **SLS UI / Stream Profiles** (stream selection without manual URLs)
- Upload progress overlay requires **Photo Pipeline** (or upload telemetry source)

### E) Photo Ingest (Inputs)

These do **not** add images to galleries directly. They only accept uploads and pass them to the Photo Pipeline.

- **FTP Server (Input):** uploads land in `/data/inbox`
- **Manual Upload Service (Input):** browser/phone uploads

#### Completed Upload Contract (V1)

Only **completed** files may enter `/data/staging`.

**Preferred (when supported by the client/server):**

- Upload into `/data/inbox/<name>.<ext>.uploading`
- On completion, atomically rename to `/data/inbox/<name>.<ext>`
- Then atomically move/rename into:
  - `/data/staging/<name>.<ext>`

**Fallback (camera/client limitations): size-stability gate**

Because some camera FTP clients may not support temp extensions or atomic rename semantics, the input layer must support a stability-based completion check:

- A file in `/data/inbox` is considered complete when its **size has not changed for 3 seconds**.
- Only then is it moved to `/data/staging`.

Notes:

- The move from inbox → staging should be an atomic rename on the same filesystem when possible.
- The pipeline must ignore `/data/inbox` entirely; it only processes `/data/staging`.

**Dependency:** FTP and Manual Upload are only useful when **Photo Pipeline** is enabled.

### F) Photo Pipeline (Required for all images)

The Photo Pipeline is the **single source of truth** for:

- when an image is considered **complete**
- what files are considered **publishable**
- how metadata is extracted and represented for overlays and StreamerBot

It processes files that arrive in:

- `/data/staging` (complete uploads only)

> Partial/temporary uploads must remain in `/data/inbox`. The **FTP input** and **Manual Upload** services are responsible for moving completed files to `/data/staging` (ideally via atomic rename).

#### V1 State Machine

`INBOX (partial) → STAGING (complete) → PROCESSING (claimed) → NORMALIZE/EXTRACT → PUBLISH → (optional) DISCORD → ARCHIVE | QUARANTINE`

The pipeline atomically claims staged files into `/data/processing`. Claim directories preserve the
original filename and are retried after a restart. See
[`ADR 0007`](../adr/0007-photo-pipeline-processing-contract.md) for the frozen V1 ownership and
recovery contract.

#### V1 Publish Rules

- Only images that can be converted to **JPG** are publishable in V1.
- JPEG, PNG, WebP, and TIFF are the reliable V1 input set.
- HEIC/HEIF is accepted only when the installed image runtime reports decoder support.
- RAW formats are **not** processed in V1 (quarantine instead). RAW support is a V2 goal.
- If EXIF is missing, sidecars are still created with placeholders.
- Default safety limits are 50 MiB per input and 80 megapixels after decode. Both are configurable.

#### Output Location

Published outputs go to the current day folder:

- `/data/galleries/YYYY-MM-DD/`

**Multi-day runtime rule (V1):**

- After computing `YYYY-MM-DD` (using `.env TIMEZONE`), the pipeline:
  - ensures `/data/galleries/YYYY-MM-DD/` exists
  - publishes the image, sidecars, and final `.ready` manifest into that dated folder
- UI routes should treat `DATA_ROOT/state/latest.json.date_folder` as the canonical selector for the active day folder.

#### Base Naming

`<base>` is derived from the original filename so operators can search by camera/phone file name.

V1 format:

- `<original>_YYYY-MM-DD_HH_mm_ss`

Where:

- `<original>` is the original filename **without extension**, sanitized for filesystem safety
- `YYYY-MM-DD_HH_mm_ss` is the **processing completion timestamp** (derived using `.env TIMEZONE`)

Example:

- `DSC_0421_2025-12-29_21_14_07`

Collision handling (V1):

- If `<base>` already exists in the target day folder, append a short suffix: `_2`, `_3`, etc.

#### Processing Steps (V1)

When a new file appears in `/data/staging`:

1. **Identify file type**

   - If file is not an image → **QUARANTINE** with `<base>.error`

2. **Determine target day folder**

   - Use the **current local date** at the time processing completes → `YYYY-MM-DD`
   - The local date is derived from the `.env` \`\`\*\* (TZ)\*\* setting to ensure consistent behavior across hosts and containers.
   - Rationale: ensures all images uploaded during a stream session land in **"today"** regardless of when they were taken.
   - Create `/data/galleries/YYYY-MM-DD/` if missing

3. **EXIF extraction** (best-effort)

   - Export full metadata to:
     - `/data/galleries/YYYY-MM-DD/<base>.json`
   - If no EXIF:
     - still write `<base>.json` with placeholders (e.g., `{ "exif": "unknown" }`)

4. **Normalize to JPG**

   - If already JPG/JPEG, validate it can be decoded.
   - If convertible (HEIC/PNG/etc.), convert to JPG.
   - Write the image to:
     - `/data/galleries/YYYY-MM-DD/<base>.jpg`
   - On conversion failure:
     - retry up to **3 attempts**
     - then **QUARANTINE** with `<base>.error`

5. **Create StreamerBot sidecars**

   - Formatted camera settings text:
     - `/data/galleries/YYYY-MM-DD/<base>.txt`
     - If unknown, write `(unknown)` placeholders.
   - Orientation flag:
     - `/data/galleries/YYYY-MM-DD/<base>.orientation`
     - `0` = landscape, `1` = portrait
     - Determined from final JPG dimensions (portrait if height > width).

6. **Create ****\`\`**** manifest (must be last)**

   Location:

   - `/data/galleries/YYYY-MM-DD/<base>.ready`

   Contents (line-based):

   - Line 0: full host path to JPG
     - `DATA_ROOT/galleries/YYYY-MM-DD/<base>.jpg`
   - Line 1: full host path to TXT (used directly as an OBS text source)
     - `DATA_ROOT/galleries/YYYY-MM-DD/<base>.txt`
   - Line 2: orientation flag (`0` or `1`)

   **Atomic write rule:** `.ready` is written to a temp name then renamed into place.

7. \*\*Update \*\*\`\`

   - Update `DATA_ROOT/state/latest.json` only after `.ready` is present.
   - Write should be atomic (temp + rename).

8. **Cleanup**

   - Move or delete the staged source file after successful publish.
   - Optionally move the original into `/data/archive/` for retention.

#### Quarantine Contract

On rejection, move the original into:

- `/data/quarantine/`

And write an error descriptor:

- `/data/quarantine/<base>.error.json`

##### `error.json` schema (V1)

```json
{
  "reason_code": "PPL-01",
  "reason": "NOT_IMAGE",
  "detail": "Detected file type did not match an image container; conversion was not attempted.",
  "original_name": "IMG_1234.MOV",
  "detected_mime": "video/quicktime",
  "attempts": 0,
  "timestamp": "2025-12-29T21:14:07-06:00",
  "log_ref": "frame-pipeline-photos:2025-12-29T21:14:07-06:00:job-7f3a"
}
```

##### Reason codes (V1)

Codes are stable and machine-readable; `detail` provides human context.

- **PPL-01 — NOT\_IMAGE**
  - File is not an image (or could not be identified as an image)
- **PPL-02 — CONVERT\_FAILED**
  - File failed conversion after max attempts
- **PPL-03 — RAW\_UNSUPPORTED**
  - File appears to be a RAW format (V1 does not process RAW)
- **PPL-04 — DECODE\_FAILED**
  - File claims to be JPG/PNG/etc. but cannot be decoded (corrupt/truncated)
- **PPL-05 — EXIF\_EXTRACT\_FAILED**
  - EXIF extraction step failed (publish may still proceed with placeholders unless other failures occur)
- **PPL-06 — FILE\_ACCESS\_ERROR**
  - Permission/locking/read error while processing
- **PPL-07 — PIPELINE\_INTERNAL\_ERROR**
  - Unexpected exception; catch-all

##### Notes

- `detected_mime` is the best-effort detected media type (e.g., `image/jpeg`, `image/heic`, `application/octet-stream`). It helps answer "what did we think this was?".
- `log_ref` is a lightweight log pointer (container name + timestamp + job id). Full stack traces are optional and may live only in logs.

Rejected files do **not** update `latest.json`.

#### Parallelism & Throughput (V1)

- Pipeline processes multiple files concurrently using a bounded worker pool.
- Default concurrency should be conservative (e.g., 2–4 workers) to avoid I/O thrash.
- Per-file output generation must remain ordered such that `.ready` is always last.

#### Discord Webhook Sink (Optional)

If Discord is enabled:

- After `.ready` is written:
  1. Create a Discord-safe copy in:
     - `/data/discord/<base>_discord.jpg`
     - Ensure image is compressed to be under **10 MB**
  2. Send via webhook with the formatted camera settings from `<base>.txt`

Rate-limiting rules (V1):

- Use a separate bounded queue for Discord sends.
- Respect webhook rate limits by throttling and retrying on 429.
- Do not block photo publishing on Discord failures; failures should be logged and retried.
- \*\*After a successful Discord webhook post, delete the corresponding file from \*\*\`\` to avoid re-sends and unbounded disk growth.

**Dependencies:**

- Requires at least one input enabled: **FTP Server and/or Manual Upload**

### G) Today Gallery + Viewer

- Gallery for today’s images
- Fullscreen viewer (OBS-friendly)

#### FRAME Gallery Integration (V1)

`frame-gallery` serves a read-only gallery from `/data/galleries/YYYY-MM-DD/`. It lists only
publications with a final `.ready` manifest and generates WebP thumbnails in
`/data/gallery-cache/YYYY-MM-DD/`.

`/today/gallery` is the multi-day album index and `/today/gallery/YYYY-MM-DD/` is the direct,
automatically updating gallery for one published day. `/today/` redirects to the latest published
day. No iframe wrapper is used.

#### Thumbnail Strategy (V1)

The gallery generates thumbnails automatically on request and stores them outside the immutable
published day folders. The Viewer Remote (`/today/remote`) sources its optional thumbnail from the
gallery thumbnail route. This is **best-effort**: if the thumbnail does not yet exist, the remote
shows nothing. No separate thumbnail generation step is added to the pipeline.

**Dependency:** requires **Photo Pipeline**

### I) Audio Monitor (V1 – Browser Capture)

**V1 approach:** Audio capture is performed **in-browser** on the LAN host using WebRTC (`getUserMedia`) and a virtual audio cable/VoiceMeeter-provided virtual input device.

#### Audio Transport (V1)

Browser capture uses **MediaRecorder** to encode audio from `getUserMedia`, sending binary chunks over a **WebSocket** connection to the `frame-audio` server. The server pipes the incoming stream to **ffmpeg**, which encodes to AAC and segments into HLS.

Flow:

```
Browser (getUserMedia → MediaRecorder) → WebSocket chunks → ffmpeg → HLS segments → /audio/hls/<streamId>/
```

#### Output Transport (V1)

- Relay outputs **HLS (AAC)** for listening.
- HLS segments target **1 second** duration to keep monitoring latency low.
- **Bitrate selection (V1):** Admin can set a per-stream target bitrate (preset list, e.g., 64k / 96k / 128k).
  - Implementation note: this is applied by the encoder (ffmpeg) as a fixed bitrate per stream. True “dynamic bitrate” adaptation is a V2 item (would require ABR ladders or congestion-aware transport).

#### Publisher Model (V1)

- **One publisher per stream**. If a publisher is active, additional publishers are rejected.

#### Pages

- `/audio/admin` — Create/manage audio streams (SLS-like) (**LAN-only**)
- `/audio/capture/<streamId>` — Capture/publisher page (**LAN-only**)
- `/audio/listen/<streamId>` — Listener page (tunneled in Hybrid)
- `/audio/hls/<streamId>/...` — HLS playlist/segments (tunneled in Hybrid)

#### Stream ID Management (V1)

- **Rename streamId (V1 recommendation):** treat rename as **create a new stream + delete the old stream**.
  - Rationale: the streamId is embedded in URLs, HLS folder paths, and any saved OBS/browser bookmarks. “True rename” requires migrating state and ensuring old URLs don’t break unexpectedly.
  - UX: provide an **“Duplicate / Rename”** flow that:
    1. creates a new stream with the new id (copying settings like listener limit, bitrate preset, always-on)
    2. shows the new Capture/Listen URLs
    3. offers a final “Delete old stream” button

#### Admin UX (`/audio/admin`)

- “Add audio source” button
- Fields:
  - `streamId` (unique)
  - Listener limit (cap)
  - Always-on mode (silence when offline)
- Actions:
  - Create stream
  - **Delete stream** (removes it from registry and stops its relay)
  - View listen URL
  - View capture URL (LAN)

#### Capture UX (`/audio/capture/<streamId>`)

- Device dropdown (WebRTC device list)
- “Go Live” button
- Real-time health:
  - input metering
  - encoder bitrate/health
  - publish/reconnect status
- **Disconnect listeners** (admin/publisher-side force re-sync)
  - Implementation note: listeners are not truly “kicked” at the transport layer (HLS is pull-based), so this action invalidates the current playlist path by incrementing a `generation` value for the stream (e.g., `/audio/hls/<streamId>/<gen>/index.m3u8`). Listen pages auto-detect and reconnect.
- Optional: “Pop-out mini window” for OBS Window Capture

#### Listen UX (`/audio/listen/<streamId>`)

- Auto-play attempt; provides “Tap to listen” if required by browser policy
- Always-on listening:
  - stream continues with injected silence when capture is offline
- Shows status + listener count

#### Exposure Rules

- **LAN-only:** `/audio/admin/*`, `/audio/capture/*`
- **Hybrid/public:** `/audio/listen/*`, `/audio/hls/*` (through Cloudflare Tunnel)

#### Notes

- No authentication in V1; `streamId` is treated as an unguessable token.

### J) Discord Audio Bridge (Optional)

`frame-audio-bridge` is a Discord bot and web service that joins a guild voice channel, receives
Discord voice audio, and creates independent per-streamer mixes for OBS.

It is separate from the browser-capture/HLS `frame-audio` monitor:

- `frame-audio` publishes browser-captured audio for remote listeners.
- `frame-audio-bridge` publishes Discord voice mixes and speaking overlays into OBS browser sources.

#### Stable URLs and Sessions

Each authorized streamer profile owns permanent, random bridge URLs:

- `/bridge/<bridge-key>/audio` - visually blank OBS Browser Source that plays the mixed audio
- `/bridge/<bridge-key>/overlay` - transparent speaking-user OBS overlay
- `/bridge/<bridge-key>/control?token=<control-token>` - private mobile control page

Discord voice sessions are temporary. Starting or stopping a session does not change the OBS URLs.
Multiple streamers in the same guild channel share one Discord receiver while retaining separate
mute, volume, delay, hide, and overlay settings.

#### Discord Commands

- `/frame info`, `/frame links`, `/frame start`, `/frame stop`, `/frame status`,
  `/frame control`, and `/frame reset-links`
- `/frame-admin setup` and `/frame-admin invite`

Administrators have access by default. An optional operator role grants streamer access without
granting Discord administrator permissions.

#### Security and Exposure

- Discord bot and control tokens remain server-side.
- Audio and overlay URLs use random, unguessable bridge keys and may optionally require a readonly
  OBS token.
- Control pages always require the profile control token.
- In Hybrid mode, `/bridge` may be publicly exposed only when `frame-discord-audio-bridge` is
  enabled.

#### Persistence and Deployment

- Guild configuration and streamer profiles persist under the service `DATA_DIR`.
- The implemented service source and standalone Docker Compose deployment live in
  `services/frame-audio-bridge/`.
- Default standalone host port: `3728/tcp`.

### D) `latest.json` (V1)

Location: `DATA_ROOT/state/latest.json`

Updated atomically by the Photo Pipeline after each successful publish and after every Gallery
Admin trash, restore, or permanent-delete operation.

#### Fields

| Field | Type | Required | Format / Notes |
|---|---|---|---|
| `updated_at` | string | yes | ISO 8601 UTC visible-library revision. Advances after publishes and management changes. |
| `date_folder` | string | yes | `"YYYY-MM-DD"` — canonical active day folder |
| `latest_base` | string | no | `<base>` name of the most recently published image (no extension, no path). Null/absent if no image published today. |
| `count_today` | integer | no | Total visible published images in `date_folder`. 0 or absent if none. |
| `latest_photo_at` | string | no | ISO 8601 UTC publication time for `latest_base`; unaffected by later management changes. |

**Example:**

```json
{
  "updated_at": "2025-12-29T03:14:07Z",
  "date_folder": "2025-12-29",
  "latest_base": "DSC_0421_2025-12-29_21_14_07",
  "count_today": 14,
  "latest_photo_at": "2025-12-29T03:13:58Z"
}
```

**Field notes:**

- `updated_at` uses UTC and acts as the change signal for all visible photo state. Consumers refresh
  when it changes, including after Gallery Admin operations.
- `latest_base` is the identifier connecting all sidecars (`.jpg`, `.txt`, `.orientation`, `.ready`). Consumers reconstruct paths as `DATA_ROOT/galleries/<date_folder>/<latest_base>.<ext>`. This name is consistent with the viewer's own `current_base` state broadcast.
- `count_today` lets UI components (viewer, remote, portal status) know the visible list size without scanning the directory.
- A publication is visible when `<base>.ready` exists and `<base>.trashed.json` does not.

#### Day-boundary semantics (Draft, in progress)

To keep operator experience simple ("it just works"), day transitions are automatic and based on the configured local timezone (`.env TIMEZONE`):

- The Photo Pipeline computes the publish `date_folder` from the current local date in `.env TIMEZONE`.
- If computed date differs from `latest.json.date_folder`, the pipeline MUST:
  1. Create `/data/galleries/YYYY-MM-DD/` for the new local day.
  2. Publish the image and sidecars into the new folder.
  3. Write `latest.json` with:
     - `date_folder` = new local day
     - `latest_base` = published image base
     - `count_today` = `1`
     - `updated_at` = publish completion timestamp (UTC)
- If local day is unchanged, the pipeline updates `latest.json` with incremented `count_today` and new `latest_base`.
- `latest.json` is updated only after successful publish (`.ready` present). Rejections do not update
  `latest.json`. Gallery Admin trash, restore, and permanent-delete operations also advance
  `updated_at` after recalculating visible state.

Consumer rule:

- UIs treat `latest.json.date_folder` as canonical active day; they MUST NOT recompute "today" from client clock.

## 5.0 - Network Exposure

### A) Design Principle

- **Traefik is the single HTTP edge** for all web UIs.
- In **Hybrid mode**, Cloudflare Tunnel exposes only HTTP/HTTPS routes.
- Non-HTTP services (SRTLA UDP ingest, FTP) remain LAN-only.

### B) Host-Exposed Ports (Documented Defaults)

> These are the default ports the installer must validate for conflicts based on enabled capabilities.

#### Always (when Portal/Web is enabled)

- **80/tcp**  — Traefik HTTP
- **443/tcp** — Traefik HTTPS

> V1 default: Traefik serves **HTTPS on LAN** by default to keep the menu system cohesive and consistent.

#### SRTLA Receiver (when enabled)

- **5000/udp** — SRTLA ingest
- **4001/udp** — SRT ingest
- **4000/udp** — Watch/play
- **8080/tcp** — Stats endpoint (recommended LAN-only; can be internal behind Traefik if desired)

#### SLS Management UI (when enabled)

- Prefer **internal behind Traefik** (no host port).
- If direct exposure is required (not recommended): **3000/tcp**

#### FTP Input (when enabled)

- **21/tcp** — FTP control
- **30000–30100/tcp** — Passive range (configurable)

#### Discord Audio Bridge (when directly exposed)

- Prefer **internal behind Traefik**.
- Standalone/default direct exposure: **3728/tcp**

#### FRAME Portal (when directly exposed)

- Prefer **internal behind Traefik**.
- Standalone/default direct exposure: **3730/tcp**

### C) Exposure by Mode

#### LAN Mode

- Web UIs available on LAN via Traefik (80/443).
- SRTLA UDP ports exposed on LAN.
- FTP exposed on LAN.
- LAN-only pages remain accessible locally:
  - `/audio/admin/*`, `/audio/capture/*`

#### Hybrid Mode

- Cloudflare Tunnel exposes only Traefik HTTP routes.
- SRTLA UDP ports remain LAN-only (user may optionally port-forward manually).
- FTP remains LAN-only.
- Public/tunneled routes include:
  - `/dashboard`, `/status`
  - `/auth`
  - `/stats/*` unauthenticated read-only stream telemetry for third-party stats integrations
  - `/overlays/view/*`, `/overlays/assets/*`
  - `/today/*`
  - `/photos/*` behind shared FRAME authentication
  - `/audio/listen/*`, `/audio/hls/*`
  - `/bridge/*` when `frame-discord-audio-bridge` is enabled
  - `/belabox/remote/*` behind shared FRAME authentication when `frame-belabox-manager` is enabled
  - `/mqtt/*` and `/belabox-chunks/*` for Belabox agent transport when `frame-belabox-manager` is enabled
- Explicitly excluded from tunnel:
  - `/slsui/*` stream management
  - `/audio/admin/*`, `/audio/capture/*`
  - `/overlays/setup`, `/overlays/api/*`
  - `/belabox`, `/belabox/api/*`, `/belabox/assets/*`
  - `/pipeline`
- External Hybrid misses and downstream `4xx`/`5xx` responses use shared FRAME error pages rather
  than bare gateway responses.

#### Hybrid Exposure Artifact (Generated by Installer)

In Hybrid mode, the installer generates the cloudflared ingress rules from `stack-config.json` capabilities.

- When a capability is enabled, its allowed public routes are added.
- When a capability is disabled (or when switching to LAN mode), the installer rewrites the tunnel config to remove those routes.

Mode switching:

- Switching **Hybrid → LAN** disables/removes the `frame-tunnel` service and deletes/rewrites the generated tunnel config so no HTTP routes remain exposed.
- Switching **LAN → Hybrid** re-enables `frame-tunnel` and regenerates ingress rules.

#### V1.1 Exposure Computation (Deterministic)

In **HYBRID** mode, the installer computes an *effective* public allowlist:

- Start with `public_route_prefixes` from `stack-config.json`
- Normalize and de-duplicate prefixes (e.g., `/today` makes `/today/gallery` redundant)
- Intersect with capability-based allowlists:
  - `/overlays/view` and `/overlays/assets` require `frame-overlays`
  - `/stats` requires `frame-video-relay`
  - `/today` requires `frame-photo-todaytools`
  - `/gallery` requires `frame-photo-gallery`
  - `/audio/listen`, `/audio/hls`, `/audio/assets`, and `/audio/public` require `frame-audio-relay`
  - `/bridge` requires `frame-discord-audio-bridge`
  - `/belabox/remote`, `/mqtt`, and `/belabox-chunks` require `frame-belabox-manager`
- Enforce **LAN-only** exclusions (always forbidden through the tunnel):
  - `/audio/admin`
  - `/audio/capture`
  - `/overlays/setup`
  - `/overlays/api`
  - `/belabox/api`
  - `/belabox/assets`
  - `/pipeline`

If forbidden prefixes appear in `public_route_prefixes`, the installer MUST strip/ignore them and warn.

(Full rules: **Appendix B**.)

### E) Retention & Cleanup Defaults (V1)

Retention is conservative and designed to prevent partial files from lingering, while preserving artifacts useful for troubleshooting.

- `/data/inbox`
  - Delete temp/partial files older than **30 minutes**.
- `/data/staging`
  - Delete files older than **30 minutes** (these should be short-lived).
- `/data/discord`
  - Files are deleted immediately after successful webhook delivery.
  - Files that remain here are considered pending/failed sends and are retained until successfully sent.
- `/data/quarantine`
  - Retained indefinitely by default (manual cleanup by end user).
- `/data/archive`
  - Retained indefinitely by default (this is the primary archive).

> V1 assumes the operator manages disk capacity manually. No automated cleanup mechanism is implemented in V1. If storage becomes low, the stack should surface warnings in `/status` and logs.

`frame-portal` reports both percentage used and free bytes for the configured `DATA_ROOT`. Warning,
error, and minimum-free-space thresholds are configurable. FRAME services must never automatically
delete archive, quarantine, or published gallery data without an explicit operator retention policy.

### 2) Normalization rules (installer-owned)

The installer is responsible for maintaining a *normalized* config on disk.

#### 2.1 Path normalization
For every route value and public prefix:
- MUST start with `/`.
- MUST NOT contain `..`.
- SHOULD NOT end with `/` unless the route is literally `/`.

#### 2.2 Prefix set normalization
The installer SHOULD collapse redundant prefixes:
- If `/today` is present, `/today/gallery` is redundant and removed.
- If `/overlays/view` is present, `/overlays/view/example` is redundant and removed.

#### 2.3 Route key aliasing (migration helper)
If older configs include legacy keys (e.g., `sls_ui`), the installer MAY map them to canonical keys on save:
- `sls_ui` → `video_relay_ui`

### 3) Dependency enforcement (capability-level)

V1 describes installer-enforced dependencies and cascading disables. V1.1 restates them using the canonical capability names above.

#### 3.1 Dependencies
- `frame-overlays` REQUIRES `frame-video-relay`.
- `frame-photo-gallery` REQUIRES at least one photo input (`frame-photo-ftp` OR `frame-photo-webupload`).
- `frame-photo-todaytools` REQUIRES at least one photo input (`frame-photo-ftp` OR `frame-photo-webupload`).
- `frame-photo-discord` REQUIRES at least one photo input (`frame-photo-ftp` OR `frame-photo-webupload`).
- `frame-video-relay` MAY be enabled without overlays.
- `frame-discord-audio-bridge` MAY be enabled independently of all other media capabilities.
- `frame-pipeline-photos` is an internal required service, not a user-facing capability. Enabling
  any implemented photo capability automatically activates its Compose profile.

#### 3.2 Cascading disables
If a base dependency is turned off, dependent capabilities MUST be turned off automatically.
The installer MUST warn the operator about cascading changes before saving.

#### 3.3 Data safety
Disabling capabilities MUST NOT delete user data. Only an explicit `reset` path removes
repository-local `/data`; external absolute data roots remain intact.

### 4) Hybrid exposure computation

#### 4.1 Design principle
- Traefik is the single HTTP edge for all UIs.
- In HYBRID, Cloudflare Tunnel exposes **only** selected HTTP route prefixes.
- Non-HTTP services (SRTLA UDP ingest, FTP) remain LAN-only.

#### 4.2 Allowed public prefixes by rule
When `mode=HYBRID`, the **effective** public exposure is:

`effective_public_prefixes = normalize(public_route_prefixes) ∩ allowed_prefixes_by_capabilities`

Where `allowed_prefixes_by_capabilities` includes:

- Always allowed (when Portal exists):
  - `/dashboard`, `/status`
  - `/auth`
  - `/assets`, `/api/portal` (Portal support routes)
- If `frame-overlays`:
  - `/overlays/view`, `/overlays/assets`
- If `frame-video-relay`:
  - `/stats` (read-only telemetry; `/slsui` management remains LAN-only)
- If `frame-photo-gallery`:
  - `/gallery`
- If `frame-photo-todaytools`:
  - `/today`
- If `frame-audio-relay`:
  - `/audio/listen`, `/audio/hls`
  - `/audio/assets`, `/audio/public` (listener support routes; no admin mutation API)
- If `frame-discord-audio-bridge`:
  - `/bridge`
- If `frame-belabox-manager`:
  - `/belabox/remote` (FRAME-login-protected remote belaUI)
  - `/mqtt`, `/belabox-chunks` (agent transport routes)

#### 4.3 Explicitly forbidden in Hybrid
Even if present in config, the installer MUST NOT expose these via tunnel:
- `/audio/admin`
- `/audio/capture`
- `/overlays/setup`
- `/overlays/api`
- `/belabox/api`
- `/belabox/assets`
- `/pipeline`

The installer MUST strip or ignore forbidden prefixes in HYBRID and emit a warning.

---

### 5) Mode switching rules

#### 5.1 LAN mode
- All web UIs reachable on LAN through Traefik.
- LAN-only pages remain available locally (`/audio/admin/*`, `/audio/capture/*`).

#### 5.2 HYBRID mode
- `frame-tunnel` is enabled.
- The installer generates cloudflared ingress rules from `stack-config.json` (using the exposure computation above).
- Only `effective_public_prefixes` are tunneled.

#### 5.3 Switching HYBRID → LAN
When `mode` changes from HYBRID to LAN, the installer MUST:
1. Disable/remove `frame-tunnel` from the compose deployment.
2. Delete or rewrite the generated tunnel config so **no** HTTP routes remain exposed publicly.
3. Leave `/data` intact.

#### 5.4 Switching LAN → HYBRID
When `mode` changes from LAN to HYBRID, the installer MUST:
1. Validate tunnel prerequisites (e.g., token present).
2. Enable `frame-tunnel`.
3. Regenerate ingress rules using the current config and capabilities.

---

### 6) Validation and failure behavior

#### 6.1 Config validation
The installer and Portal MUST validate `stack-config.json` at startup.
If invalid:
- Portal SHOULD show a clear error page with what failed and how to re-run installer.
- Installer MUST refuse to apply invalid config.

---

### 6.2) Time semantics for day management (Draft, in progress)

To avoid ambiguity and cross-environment drift:

- **Day partitioning** (folder naming and rollover) uses `.env TIMEZONE`.
- **Machine timestamps** (`latest.json.updated_at`, `/status/api.generated_at`, and other event times) remain ISO 8601 UTC.
- Implementations SHOULD expose localized display time in UI only; contracts remain UTC for interoperability.

#### 6.3 Common validation checks
- `mode` is one of `LAN|HYBRID`.
- All canonical capability keys exist and are booleans.
- All canonical route keys exist and route values start with `/`.
- `public_route_prefixes` is a unique list of `/...` strings.
- In HYBRID:
  - forbidden prefixes (`/audio/admin`, `/audio/capture`, `/overlays/setup`, `/overlays/api`, `/belabox/api`, `/belabox/assets`, `/pipeline`) are removed/ignored with warning.
  - `effective_public_prefixes` must not be empty unless operator explicitly confirms (optional).

### 8) Scenarios (how this behaves)

#### Scenario A — Fresh HYBRID install
- `mode=HYBRID`, all capabilities true, `public_route_prefixes` set to defaults.
- Public access works for `/today/*`, `/photos/*`, `/overlays/view/*`, `/gallery/*`, `/audio/listen/*`, `/audio/hls/*`.
- `/audio/admin/*`, `/audio/capture/*`, `/overlays/setup`, `/overlays/api/*`, and `/pipeline` remain LAN-only.

#### Scenario B — HYBRID → LAN “pull the plug”
- Operator sets `mode=LAN`.
- Installer removes/disables `frame-tunnel` and clears tunnel ingress.
- All services continue to work on LAN via Traefik; no public exposure remains.

#### Scenario C — Disable overlays while staying HYBRID
- Operator sets `frame-overlays=false`.
- Installer removes `/overlays/view` and `/overlays/assets` from the effective tunnel allowlist and updates nav status.
- Today + gallery + audio listen can remain public if still enabled.

#### Scenario D — Misconfigured public prefixes include LAN-only routes
- Config mistakenly includes `/audio/admin` in `public_route_prefixes`.
- Installer strips it in HYBRID, warns, and proceeds without exposing it.

#### Scenario E — Route drift
- Operator changes `routes.video_relay_ui` path but forgets to update public prefixes.
- Local nav still works (routes drive nav), but public exposure might not include the new path.
- Recommendation: treat `public_route_prefixes` as installer-managed/derived, not hand-edited.
